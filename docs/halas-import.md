# Halas geometry import

## Source

- Reference input: `resources/LanternExtractor/Exports/halas/Zone/halas.glb`
- Runtime copy: `assets/imported/halas/halas.glb` plus its extracted PNG
  texture sidecars
- Format: embedded glTF 2 binary (`.glb`), 2.1 MB
- Import policy: referenced directly as a Godot imported scene. The runtime
  does not invoke LanternExtractor and the source file is never modified.

## Current integration

`data/halas.json` selects the runtime copy through `geometry_scene`; the game
instantiates it as the world geometry. `resources/.gdignore` ensures Godot
does not scan the reference sources. The source GLB has a `0.1` root transform,
while the companion character GLBs retain native game-scale units.
`geometry_scale: 10.0` cancels only that zone reduction, preserving the
intended zone-to-character ratio without modifying the extracted source file.

### Static object placements

`data/halas_objects.json` is an unmodified runtime copy of Lantern's
`object_instances.txt` manifest. It contains 445 instance records for 91
unique static-prop models. Only those referenced GLBs are copied to
`assets/imported/halas/objects/`; the placement loader reads each record's
source position, complete `RotX`/`RotY`/`RotZ` orientation, and scale. The
complete orientation is transformed through Halas' X-mirrored object
coordinate frame rather than reducing source placement to yaw alone.

This covers Lantern's world-object data, not NPC spawns. The supplied EQEmu
checkout contains server code but no populated content database from which
Halas NPC spawn records can be exported.

### Merchant listings

`data/halas_merchants_source.json` contains 735 classic-filtered listings for
the 40 merchant IDs referenced by the Halas NPC snapshot. It intentionally
does not claim item names, prices, stock behavior, or faction outcomes: those
require a reviewed neutral item/faction import before a merchant UI is added.
`tools/validate_halas_merchant_data.py` gates the snapshot's provenance,
roster linkage, slots, access fields, and numeric ranges so it remains safe
for that future integration.

At runtime, each placed prop's imported mesh is also given exact triangle
collision at its source position, rotation, and scale. This follows the client
reference approach of combining placed-object triangles with zone terrain for
movement and camera obstruction. Props are kept on a separate physics layer so
they do not contaminate the terrain-only NPC elevation audit.

Repeated placements reuse one cooked Godot trimesh shape for each shared,
reflection-baked runtime mesh. Each placement still receives its own static
body and transform, so collision remains exact while zone startup avoids
recooking the same immutable prop geometry hundreds of times.

### Classic NPC source snapshot

`data/halas_npcs_source.json` is generated by
`tools/import_peq_halas.py` from a separately downloaded ProjectEQ content
archive. The importer includes only base-zone spawns that are available in
original EverQuest (expansion `0`) and have no event content flags. Its current
snapshot contains 68 complete spawns, 68 NPC types, and five valid Halas
patrol grids; 25 later-expansion or event spawns, one incomplete source row,
and eight cross-zone path-grid references are excluded. The source metadata is
embedded in the JSON and identifies the exact archive and filter.

ProjectEQ is a useful structured source, but it is not represented as an exact
P1999 database. `data/halas_npcs_overlay.json` is the versioned correction
contract for reviewed roster, path, stat, and behavior changes. Run
`python3 tools/apply_halas_npc_overlay.py` after either input changes; it
validates every referenced ID and field before regenerating the derived runtime
snapshot `data/halas_npcs.json`. The checked-in overlay is deliberately empty:
it establishes provenance and the review path without fabricating P1999 facts.

### Runtime population

`scripts/halas_npc_population.gd` instantiates the derived runtime snapshot
through `data/halas.json`. It resolves every actor from its source `race`, `gender`,
`texture`, and `face` fields: Halas citizens use `hlm`/`hlf`, Barbarians use
`bam`/`baf`, Humans use `hum`/`huf`, sled dogs use `wol`, and the ferry uses
`hferry`. `tools/export_halas_character_variants.sh` reproducibly exports only
the skin/head combinations the selected roster requires. Values beyond a
classic model's actual variant table are clamped until armor/equipment
appearances are represented separately. The one non-visible server helper is
kept data-only. Server coordinates use `[x, y, elevation]` and convert to the Halas
scene as `(-y, elevation, x)`. The collision audit validates all 67 visible
static spawns and all 178 points of the five retained patrols against authored
Halas terrain.

Visual scale resolves `npc_types.size` through EQEmu's
`GetRaceGenderDefaultHeight` when it is unset, then normalizes every individual
Lantern rig to that resolved native EQ height. The scale is therefore
`resolved server size / measured loaded GLB height`, not an assumption that
a raw GLB scale of `1.0` is game scale. Halas sled dogs, for example, resolve
to 3 feet versus the wolf default of 4. The model is grounded at its measured
feet and its nameplate is placed above the resolved height.

Actors with a grid move through its ordered waypoints and honor each waypoint's
pause in seconds. The shipped humanoid and wolf GLBs are rebuilt through
Lantern's intermediate skeletal pipeline, combining each Halas mesh with its
client animation source. They include original idle, walk, attack, and death
clips. The revised recipe also embeds the source swim stroke (`L06`, fallback
`L09`) and tread-water idle (`L08`, fallback `P07`) clips; the runtime selects
them for a player in water. The player HLM asset is rebuilt with these original
clips. The ferry has no skeletal source and remains a static model.
The runtime HLM, HLF, WOL, Human, and Barbarian assets are exported with
`LanternExtractor/tools/eqmob-gui/backend/eqmob_glb.py`, rather than the older
standalone converter. Its per-body-part V-flip corrections are required for
the Halas body, face, limb, and wolf texture regions; this changes GLB UVs
only and never alters the source PNGs.
The GUI converter also resolves HLF's legacy `hufbi_l` skeleton-bone name to
the shared ELF animation track `bi_l`. Without that alias, the female model's
left arm remains in a mismatched bind pose while every other bone animates.
Because the extracted character meshes use different root pivots, the runtime
also grounds each model's lowest rendered bound at the server-recorded
elevation. This prevents a correct `spawn2.z` location from visibly floating
or sinking solely due to model-export pivot differences.

`tools/validate_halas_spawn_coordinates.py` verifies named source rows against
published P1999 `/loc` values. The client displays locations as `(Y, X)` while
the server stores `(X, Y, elevation)`. A runtime collision audit tests all
axis/sign candidates against the exported Halas terrain. The only mapping that
aligns all static source spawns to authored floor geometry is
`(-server_y, elevation, server_x)`.

`tools/validate_halas_asset_scale.py` is the scale/provenance gate. It verifies
that the runtime Halas GLB, every runtime prop GLB, and the 445 placement rows
are byte-identical to their Lantern exports. It also verifies that the zone
GLB's authored `0.1` root scale is cancelled exactly by
`geometry_scale: 10.0`. Prop instances preserve all three manifest scale
components without a global multiplier. NPC rigs are deliberately different:
they are normalized at runtime to the explicit `npc_types.size` source value,
or to EQEmu's race/gender default only when that value is non-positive.

The player starting position is the nearby dry dock-side visual-test coordinate
(`[-13.0, 4.38, -10.0]`). `player_spawn_revision` is bumped whenever the
starting placement must override an existing local save; revision 6 resets
players who were left in the water while swimming is being revisited. The
disabled Training Spark remains a development-only test fixture.
